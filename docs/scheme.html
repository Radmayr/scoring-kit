scoring-kit 0.4 · батч-инференс на Airflow

Фабрика скоринга

Аналитик описывает процесс в одном файле pipeline.yaml. Фабрика проверяет описание и собирает из него DAG на операторах платформы. Ниже — из чего состоит система, какие сценарии она покрывает и как поднять её на работе.

наш слой операторы и сервисы платформы данные и модели ожидание проверка

Общая схема

Сверху вниз — путь от правки в конфиге до скоров в витрине. Всё, что синее, принадлежит команде и лежит в git; зелёное — платформа, которую мы не трогаем.

Что происходит внутри фабрики

входpipeline.yamlвыбран рецепт и движок
→
рецептsingle / multi / fit_applyрешает, какие блоки и в каком порядке
→
проверкаплан из блоковколонки протягиваются по графу; ошибка видна до запуска
→
адаптерыблок × движокединственное место, где живут операторы платформы
→
выходDAG.pyсамодостаточный файл, как от старого инструмента

Новый сценарий — это новый рецепт из тех же блоков. Если платформа заменит оператор, меняется один адаптер, а конфиги процессов остаются как были.

Как поднять на работе

Шесть этапов по порядку. Каждый заканчивается проверяемым результатом; следующий не начинайте, пока не выполнено условие «готово».

1

Репозитории в GitLab

Кто: владелец фабрикиВремя: полдня
  1. Создайте в GitLab группу команды и два пустых проекта: scoring-kit и scoring-pipelines.
  2. Перенесите фабрику с GitHub вместе с тегами версий.
  3. Перенесите репозиторий процессов (сейчас он у меня локально; передам удобным вам способом).
  4. В scoring-pipelines/requirements.txt замените адрес GitHub на GitLab, тег оставьте v0.3.0.
  5. Выберите способ установки пакета коллегами: SSH-ключ, deploy token с правом read_repository или wheel во внутреннем pip-индексе. Последний удобнее всего: обычный pip install scoring-kit==0.3.0.
git clone https://github.com/Radmayr/scoring-kit.git && cd scoring-kit
git remote add gitlab <адрес-проекта-scoring-kit-в-GitLab>
git push gitlab main --tags

Готово, когда в GitLab оба проекта, а pip install -r requirements.txt ставит фабрику из GitLab на чистой машине.

2

Рабочее место

Кто: каждый, кто заводит процессыВремя: 15 минут
  1. На ноутбуке (рендер и ручная публикация, пока нет CI): клонировать scoring-pipelines, поставить зависимости, проверить конфиги.
  2. В ML Core (отладка на реальных данных): поставить ту же версию фабрики, выгрузить выборку в csv и скачать файл модели из реестра.
git clone <адрес-scoring-pipelines> && cd scoring-pipelines
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
scoring validate pipelines/*/

Готово, когда scoring validate pipelines/*/ пишет OK для всех четырёх процессов.

3

Разовые настройки платформы

Кто: владелец фабрики + админ инстансаВремя: 1–3 дня (заявки)
  1. Ручные DAG'и. Всё, что вы публикуете через mlc из ~/airflow_dags, перенесите в scoring-pipelines/dags_manual/. Публикация заменяет всё опубликованное через mlc: DAG, которого нет в папке, исчезнет.
  2. Алерты. Заведите канал команды и проверьте, что сервисная учётка инстанса может в него писать: включите alerts в любом теневом DAG'е и уроните его один раз руками.
  3. DLH. Учётке из dp_conn_dlh нужны роли из README оператора (DataPlatform Access, DLH Spark user, группы на чтение и запись схем) и доступ ко всем колонкам таблицы-источника.
  4. Публикация из CI. Сервисная учётка для mlc: её ключ — в переменные CI (MLC_SERVICE_KEY, тип File), плюс MLC_PROJECT, AIRFLOW_TEST, AIRFLOW_PROD. Нужен образ раннера, в котором есть mlc.

Готово, когда тестовое падение приходит сообщением в канал, а кнопка deploy-test в CI публикует набор DAG'ов без ошибок.

4

Три сценария в тени на тестовом инстансе

Кто: владелец процессаВремя: 2–3 дня наблюдений

Теневой DAG читает те же данные, что и старый процесс, но пишет в таблицы *_shadow. Старый процесс продолжает работать как раньше.

  1. Впишите в shadow.txt процессы, которые идут в тени: pipelines/pd_model, pipelines/calib_pre.
  2. Закройте TODO в их yaml: ключ, таблицы для сенсора, полный список колонок витрины (сверьте с information_schema).
  3. Опубликуйте (кнопкой deploy-test или командой ниже), запустите теневые DAG'и вручную.
  4. После прогона старого и теневого — сверка.
# вручную, пока нет CI: на тест уходят только теневые версии из shadow.txt
# + ручные DAG'и; команда покажет список и спросит подтверждение
scoring publish --env test

# после прогонов: SQL сверки, выполнить в Greenplum
scoring compare-sql pipelines/pd_model
scoring compare-sql pipelines/calib_pre

Готово, когда сверка даёт only_in_prod = only_in_shadow = 0, n_diff_over_tol = 0, n_null_mismatch = 0 два-три дня подряд.

5

DLH-вариант одной модели

Кто: владелец процессаВремя: день + заявки на доступ
  1. В ML Core скачайте файл модели Bankrupt из реестра и упакуйте его в бандл.
  2. Загрузите бандл в Model Registry новой версией (или новой моделью) и впишите её mrid в model.mrid.
  3. Подтвердите таблицу-источник в DLH и её ключ (TODO в yaml).
  4. Опубликуйте вместе со всем набором, запустите вручную. Результат — таблица DLH: сравните скоры с витриной Greenplum по ключу в ML Core.
scoring bundle pipelines/bankrupt_phis_dlh --model model.pkl -o bundle.pkl
# необязательно: прогнать бандл локально на выборке
scoring debug pipelines/bankrupt_phis_dlh --data sample.csv --model bundle.pkl

Готово, когда check_result зелёный, а скоры DLH совпадают с витриной Greenplum.

6

Переключение и миграция остальных процессов

Кто: владельцы процессовВремя: до отключения старого инструмента
  1. Переключение одного процесса: пауза старого DAG'а → убрать процесс из shadow.txt → deploy-prod → ручной запуск и проверка витрины → старый DAG неделю на паузе (откат = снять паузу) → удалить.
  2. Остальные процессы из старого инструмента: вкладка Code в Airflow → yaml (это хорошо умеет агент) → scoring validate → тень → сверка → переключение.
  3. Навигация: после каждого изменения обновляйте каталог; CI проверяет, что он актуален.
scoring catalog pipelines/*/ -o CATALOG.md

Готово, когда в папке piper/ на инстансе не осталось живых процессов.

Три правила, которые нельзя нарушать

1. Публикуется только полный набор DAG'ов из одной папки и только после --check: всё, чего нет в папке, исчезает с инстанса. На тестовый инстанс — только теневые версии процессов: тест и прод пишут в один Greenplum.

2. Перед боевым деплоем нового процесса старый DAG ставится на паузу: два DAG'а не должны писать в одну витрину.

3. Сгенерированные DAG'и руками не правятся: правка идёт в yaml, DAG пересобирается.
